## 1. Executive Summary

In October 2026, researchers disclosed two critical vulnerabilities in the PHP language runtime, tracked as CVE-2026-109618 and CVE-2026-109619 and collectively referred to as **PHP2Shell**.

The vulnerabilities involve memory-safety failures associated with PHP's handling of exceptional conditions, including out-of-memory errors and fatal-error processing. Under vulnerable conditions, internal state can remain invalid or refer to memory that has already been released. Researchers demonstrated that these weaknesses could be chained to achieve remote code execution without authentication in representative PHP application environments. They also demonstrated the disclosure of sensitive process memory.

The vulnerabilities are significant because they exist in the PHP runtime itself rather than depending on a specific flaw in WordPress, Drupal, Joomla, or another application. Consequently, updating an individual content management system or application plugin is not a substitute for updating the underlying PHP runtime.

Amazon Threat Intelligence reported an exploitation attempt against its MadPot sensor environment on October 17, four days before public disclosure. Additional attempts were observed around the disclosure date. Amazon stated that it remained unclear whether the observed attempts would have succeeded against real-world systems. Public evidence therefore supports the existence of early exploitation attempts, but does not establish the number of successfully compromised production systems.

PHP released fixes on October 21, 2026. On October 23, the PHP project also published an advisory for a separate, related vulnerability, CVE-2026-115560, indicating that the broader issue required continued investigation beyond the original two CVEs.

**Primary CEI finding:** PHP2Shell demonstrates how low-level software defects, widespread deployment, chained exploitation, and AI-assisted vulnerability research can combine to change the practical risk of longstanding code. It is a useful case for studying the relationship between vulnerability discovery, exploit development, disclosure timing, and defensive response.

**Evidence confidence:** High for the existence and technical nature of the two vulnerabilities; high for reported exploitation attempts against monitoring infrastructure; undetermined for the overall number of successful real-world compromises.

## 3. Background and Context

### 3.1 The PHP Runtime

PHP is a server-side programming language used by a substantial portion of the web ecosystem. It supports content management systems, websites, APIs, and application backends.

The security implications of a runtime vulnerability differ from those of an isolated application vulnerability. A flaw in the runtime may affect multiple applications using the same vulnerable engine, even when those applications do not contain the original programming mistake.

### 3.2 Vulnerability Discovery

Wiz Research publicly described how AI models contributed to identifying and developing demonstrations for the PHP vulnerabilities. The research involved repeated testing, debugging, and combining multiple weaknesses into working exploit chains.

This is an important distinction for CEI: AI did not make the underlying software defect exist. Rather, AI-assisted research helped make a complex vulnerability and exploitation path more practically discoverable and reproducible.

The research also involved coordination with the PHP team and other security organizations to develop and validate fixes before public disclosure.

### 3.3 Exposure Conditions

The PHP Security Team identified PHP installations serving web requests as affected, including deployments using PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, and LiteSpeed.

The risk is particularly important for internet-facing systems that process untrusted requests. The PHP project identified mod_php as a particularly concerning configuration because a demonstrated attack path could trigger the vulnerability before application-level code executes.

**Important limitation:** The existence of a vulnerable PHP installation does not establish that it was reachable, exploitable in its particular configuration, or successfully compromised.

## 4. What Happened?

The publicly documented sequence consists of vulnerability discovery and validation, coordinated disclosure, the publication of fixes, and exploitation attempts observed by security monitoring systems.

The original flaws involve unsafe handling of memory and internal state after exceptional request-processing conditions. Under certain circumstances, later processing can encounter state that should have been cleared or reinitialized.

Researchers demonstrated that related weaknesses could be combined to obtain remote code execution in representative application environments. They also demonstrated that process memory could expose sensitive material, potentially including credentials and tokens.

AWS subsequently reported an exploitation attempt against a MadPot sensor on October 17, before the public advisory. After disclosure, AWS observed additional attempts and the rapid appearance of proof-of-concept exploits.

These observations establish that exploitation activity was not limited to theoretical research after the public announcement. However, the available reports do not establish that every attempt succeeded or that a particular organization suffered a confirmed compromise.

The PHP project released security updates on October 21. A further advisory on October 23 documented CVE-2026-115560, a separate vulnerability involving a related area of PHP functionality.

## 6. Technical Analysis

### 6.1 CVE-2026-109618 — Out-of-Memory Handling and Memory Corruption

This vulnerability involves unsafe handling of internal request data when PHP encounters an out-of-memory condition.

The exceptional condition can interrupt normal initialization and cleanup. Internal structures may consequently be left in a state that subsequent processing handles incorrectly.

Wiz reported demonstrating remote code execution in representative PHP application environments and separately demonstrated unauthenticated process-memory disclosure.

**Security implications:**
- Potential remote execution of code with the permissions of the affected PHP process.
- Potential exposure of sensitive data held in process memory.
- Risk to applications that otherwise have no corresponding application-level vulnerability.

**Assessment:** Critical runtime-level vulnerability with demonstrated impact in research environments.

### 6.2 CVE-2026-109619 — Stale Internal State and Use-After-Free

This vulnerability involves internal PHP state continuing to reference memory after that memory has been released.

Under specific conditions, a subsequent request can encounter the stale state before normal initialization resets it. This creates an unsafe condition that researchers demonstrated could be developed into remote code execution.

The weakness is classified in part as CWE-416, Use After Free, and involves improper handling of exceptional conditions.

**Security implications:**
- Potential memory corruption.
- Potential remote code execution without authentication through demonstrated attack paths.
- Increased risk when vulnerable request-processing behavior can recur in a worker that retains state between requests.

**Assessment:** Critical runtime-level vulnerability with demonstrated impact in research environments.

### 6.3 Why the Vulnerabilities Matter Together

The two CVEs represent related weaknesses in how PHP handles exceptional conditions and internal memory state. Their significance is not limited to either individual bug: researchers demonstrated that multiple weaknesses could be combined to create a more consequential attack path.

This illustrates a recurring security principle: several individually difficult-to-exploit conditions may form a practical compromise chain when they can be combined.

### 6.4 Attack Chain Assessment

**Evidence-supported high-level sequence:**

1. An externally reachable PHP service processes a request.
2. Vulnerable runtime behavior is triggered under specific conditions.
3. Internal memory or request state becomes unsafe.
4. Subsequent processing encounters the invalid state.
5. In demonstrated research scenarios, the chain can result in process-memory disclosure or remote code execution.

This is a conceptual summary of the documented behavior, not a claim that every observed exploitation attempt followed an identical chain.

**Potential interruption points:**
- Updating PHP to an appropriate fixed release.
- Reducing exposure of vulnerable internet-facing services while remediation is pending.
- Monitoring suspicious request patterns and unexpected PHP worker behavior.
- Investigating unexpected child processes, file changes, and outbound connections.

## 7. Impact Assessment

### 7.1 Technical Impact

Researchers demonstrated remote code execution in representative WordPress, Drupal, and Joomla environments. They also demonstrated process-memory disclosure.

The vulnerabilities exist in PHP itself; therefore, the implications extend beyond those three application platforms.

### 7.2 Data Impact

The demonstrated memory-disclosure behavior could expose sensitive material in PHP process memory, potentially including credentials, tokens, and API keys.

The sources reviewed do not establish that a particular organization's production secrets were stolen through these vulnerabilities. Actual data exposure must be investigated independently for each affected environment.

### 7.3 Operational Impact

Organizations using vulnerable PHP installations must identify affected systems, apply updates, and assess whether suspicious activity occurred before remediation.

For internet-facing environments, this may require urgent maintenance, service restarts, log review, incident investigation, and coordination with hosting providers.

### 7.4 Financial Impact

The sources reviewed do not establish a reliable aggregate financial loss attributable to successful exploitation of these CVEs.

Potential costs include emergency patching, investigation, recovery, credential rotation, service interruption, and security improvements. These are potential consequences, not confirmed losses for every affected organization.

### 7.5 Legal and Regulatory Impact

Potential consequences depend on the systems involved, the data affected, and the applicable legal and regulatory requirements. No specific legal finding or regulatory penalty is asserted in this report.

## 8. Root Cause and Contributing Factors

### 8.1 Primary Technical Cause

The primary technical issue was unsafe memory and internal-state handling in PHP's request-processing and exceptional-error paths.

The original vulnerabilities demonstrate how exceptional conditions can bypass assumptions made by ordinary initialization and cleanup logic.

### 8.2 Contributing Factors

- **Runtime-level exposure:** The defects existed in core PHP rather than only in an individual application.
- **Broad deployment:** PHP is used by a large number of independently managed services.
- **Complex exploitation:** Working exploit development required combining weaknesses and validating behavior through testing.
- **Shared process state:** Certain vulnerable paths involved internal state persisting between requests handled by a worker.
- **Disclosure timing:** AWS reported an exploitation attempt before the public advisory.
- **Rapid exploit development:** Public reporting described proof-of-concept development and exploitation attempts soon after disclosure.
- **Longstanding code:** Researchers reported that the relevant underlying issues had existed for many years.

### 8.3 Control Failures

The available evidence establishes flaws in the PHP runtime. It does not establish a specific control failure at every organization running vulnerable PHP.

Whether an individual deployment was exposed depends on its version, configuration, reachability, surrounding controls, and remediation status.

### 8.4 Counterfactual Analysis

A corrected PHP runtime prevents the original vulnerabilities addressed by the corresponding patches. Strong isolation and least-privilege execution can reduce the impact of a successful compromise but should not be treated as substitutes for patching.

Earlier detection may reduce the duration of an intrusion. However, the sources reviewed do not establish that a particular monitoring configuration would have prevented every demonstrated exploitation path.

## 9. Cyber Evolution Analysis

### 9.1 Automation Versus Autonomy

PHP2Shell provides evidence of AI-assisted vulnerability research, but it does not by itself establish that an autonomous AI agent conducted the observed real-world exploitation attempts.

CEI should distinguish three separate roles:

1. AI-assisted discovery and analysis by researchers.
2. AI-assisted exploit development and validation in controlled research.
3. Potential AI use by malicious actors during real-world exploitation.

The first two have public supporting evidence. The third requires separate evidence and should not be inferred merely from the technical complexity or speed of an attack.

### 9.2 Complex Vulnerability Chains

The incident demonstrates how multiple memory-safety weaknesses can be combined to produce impact beyond what an isolated vulnerability description might suggest.

For CEI, this supports studying the relationships between:
- Individual weakness characteristics.
- Preconditions required for exploitation.
- The ability to chain vulnerabilities.
- Time and expertise required to develop a working exploit.
- The availability of defensive fixes and mitigations.

### 9.3 AI and the Practical Exploitability of Old Code

Wiz reported that frontier AI models materially helped reduce the difficulty of discovering and developing working exploit chains for longstanding flaws.

The research supports the hypothesis that AI can reduce the expertise or time required for some forms of vulnerability research. It does not establish a universal rate at which AI accelerates exploitation or prove that all complex vulnerabilities have become easy to exploit.

### 9.4 Disclosure and Exploitation Timing

The October 17 attempt reported by AWS preceded the October 21 public disclosure. This demonstrates why the public advisory date cannot automatically be treated as the beginning of exploitation.

For CEI's historical records, at least three separate dates should be tracked:

- Earliest known exploitation attempt.
- First confirmed successful exploitation, if established.
- Public disclosure date.

These dates answer different questions and should never be collapsed into one event date.

### 9.5 Novelty Assessment

**Classification:** Existing vulnerability classes combined with a significant change in the practical research and exploitation context.

Use-after-free defects and memory corruption are established vulnerability classes. The more notable research question is whether AI-assisted methods materially change the time, skill, and resources required to turn such defects into working exploit chains.

## 10. CEI Research Questions

1. How much did AI reduce the time needed to discover and validate the vulnerabilities compared with a suitable non-AI research baseline?
2. Which characteristics of the vulnerabilities made them suitable for chaining?
3. How frequently do memory-safety defects in widely deployed runtimes lead to cross-application exposure?
4. How often does exploitation begin before public disclosure?
5. Does the availability of public technical details predict a measurable increase in exploitation attempts?
6. How quickly do exploitation attempts appear after patches and proof-of-concept material become available?
7. Which defensive controls are most effective at reducing exposure while patches are being deployed?
8. Can a historical dataset predict which newly disclosed vulnerabilities will attract early exploitation?
9. How can CEI distinguish an observed exploitation attempt from a confirmed successful compromise?
10. Does AI-assisted vulnerability research systematically change the relationship between vulnerability complexity and real-world exploitation?

These remain research questions. A single incident cannot establish general trends across the entire cybersecurity ecosystem.

## 11. Lessons and Defensive Implications

### 11.1 Patch the Runtime

Organizations should inventory PHP installations and apply the appropriate vendor-supported fixes. Application updates alone do not correct a vulnerable PHP runtime.

The PHP project listed these fixed release versions for the original two CVEs:

| PHP Branch | Fixed Version |
|---|---|
| 8.5 | 8.5.12 |
| 8.4 | 8.4.27 |
| 8.3 | 8.3.36 |
| 8.2 | 8.2.35 |

Older branches may require vendor-provided backports or migration to a supported release. Verify the correct package with the relevant operating-system or hosting vendor.

**Important follow-on issue:** On October 23, PHP disclosed CVE-2026-115560, which is not addressed by the October 21 releases. The PHP project recommended setting `session.upload_progress.enabled=0` while awaiting an update for that separate issue. Organizations should follow the latest official PHP advisory rather than assume the original patches resolve every related vulnerability.

### 11.2 Investigate Earlier Activity

Because AWS reported an attempt on October 17, organizations should not limit investigation to activity occurring after October 21.

Review available web-server, application, endpoint, and network telemetry for suspicious requests, unexpected processes, unusual file changes, and unexplained outbound connections.

### 11.3 Reduce Potential Impact

Apply least privilege to PHP worker accounts, isolate application environments, restrict unnecessary outbound access, and ensure that secrets are not unnecessarily exposed to application processes.

These measures reduce risk but do not replace the required security updates.

### 11.4 Improve Vulnerability Response

For critical, internet-facing vulnerabilities, organizations should be prepared to assess exposure and prioritize remediation rapidly. A public disclosure may follow earlier exploitation, and technical details can enable additional exploitation attempts soon afterward.

### 11.5 Preserve Evidence

When investigating possible compromise, preserve relevant logs and system artifacts before making changes that could destroy useful evidence. Rotate exposed credentials when there is a credible reason to believe they may have been compromised.

### Proposed Retrospective Research Experiment

CEI could investigate whether public vulnerability characteristics and disclosure information can predict early exploitation activity.

**Candidate target:** Whether a vulnerability receives independently documented exploitation attempts within a defined period following disclosure.

**Potential predictors:**
- Vulnerability severity.
- Internet exposure and deployment prevalence.
- Availability of a patch.
- Availability of public proof-of-concept material.
- Vulnerability class and exploitation prerequisites.
- Prior exploitation patterns involving similar technologies.

**Required controls:**
- Define the prediction target before evaluating the outcome.
- Preserve the exact information available at the forecast cutoff.
- Exclude future reports from the predictor dataset.
- Compare model performance with simple historical baselines.
- Distinguish observed attempts from confirmed compromises.
- Account for reporting bias and differences in telemetry coverage.

**Retrospective limitation:** PHP2Shell cannot be counted as a successful prediction unless CEI can produce a dated forecast that existed before the relevant outcome was known. The case can still be used to design and evaluate future forecasting methodology.

## 16. Final Research Assessment

**Key Finding:** PHP2Shell shows how longstanding runtime-level memory-safety defects can become practically exploitable through complex vulnerability chaining, while AI-assisted research may reduce the effort needed to develop working demonstrations.

**Primary Limitation:** Public evidence of exploitation attempts does not establish the total number of successful real-world compromises, nor does this single case establish a general causal relationship between AI capability and attack frequency.

**Research Value:** The case connects software architecture, memory safety, widely deployed infrastructure, AI-assisted vulnerability research, coordinated disclosure, and the timing of exploitation attempts. It is particularly relevant to CEI's study of how the conditions for cyber incidents evolve.

**Next Research Step:** Build a source-dated timeline and compare the PHP2Shell disclosure window against a historical dataset of critical vulnerabilities. Measure time to first observed exploitation, time to public proof of concept, patch availability, and time to defensive remediation, while accounting for differences in monitoring coverage.
